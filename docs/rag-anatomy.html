문제와 제약

아래의 모든 기술 선택은 이 두 가지에서 파생된다. 여기를 이해하면 나머지는 대부분 따라온다.

풀려는 문제

모꼬지 팀 노션에는 2년치 문서가 쌓여 있다. 기술 스택 선정 이유, 스프린트 회의록 4차수, 기획·도메인 문서, 온보딩 자료, FAQ, 외부활동 기록. 계층이 깊어서 문서 → 메뉴 → 카테고리 → 토글 → 페이지를 헤집어야 하나를 찾는다.

"그때 그거 어디 있었지"를 자연어 질문 한 번으로 끝내는 것이 목표다. 답변에는 반드시 근거 문서 링크가 붙어야 한다. 링크가 없으면 사용자가 검증할 방법이 없고, 검증할 수 없는 답은 문서 검색 도구로서 가치가 없다.

왜 파인튜닝이 아니라 RAG인가

처음 요구사항은 "파인튜닝을 어느 정도 하고"였다. 하지만 문서 QA에서 파인튜닝은 대체로 틀린 도구다. 둘은 서로 다른 것을 담당한다.

구분담당하는 것문서가 바뀌면
RAG 지식 — 무엇이 사실인가 인덱스만 갱신, 몇 분
파인튜닝 행동 — 어떤 말투로, 어떤 형식으로 재학습, GPU 필요

노션 내용을 파인튜닝으로 외우게 하면 두 가지가 망가진다. 모델이 출처를 댈 수 없게 되고 (가중치에 녹아든 지식은 어느 문서에서 왔는지 추적이 안 된다), 문서가 수정될 때마다 재학습해야 한다. 팀 위키는 매주 바뀐다.

결론

LLM 파인튜닝은 범위에서 뺐다. 검색 품질이 부족할 때 쓸 카드는 LLM이 아니라 임베딩 파인튜닝이다 — 도메인 용어(모꼬지, 그리디, 총동연, 창의학기제, 에타)를 일반 모델이 못 잡을 때 검색기 자체를 학습시키는 쪽이 훨씬 싸고 효과가 크다.

하드웨어가 설계를 결정한다

개발 PC에 외장 GPU가 없다. Intel Iris Xe 내장 그래픽이고, Ollama는 이걸 자동으로 제외한다. RAM 15.6GB는 이미 포화 상태(커밋 32GB / 46GB)라 페이지파일을 쓰고 있다.

이 제약은 "느려진다"가 아니라 "어떤 선택지는 아예 동작하지 않는다"는 뜻이다. 층위 2에서 실측으로 확인한다.

층위 1

두 개의 파이프라인

RAG 시스템은 하나의 흐름처럼 보이지만 실제로는 시간축이 다른 두 파이프라인이다. 둘은 벡터 DB 하나만 공유한다.

왜 나누는가

인덱싱은 무겁고 드물다 — 노션 전체를 훑고 수천 번 임베딩을 돌린다. 질의는 가볍고 잦다 — 벡터 하나 만들고 검색 한 번 한다. 시간 예산이 세 자릿수 배 차이 난다.

그래서 비싼 일은 전부 인덱싱 쪽으로 밀어넣는 게 설계 원칙이다. 청킹, 컨텍스트 헤더 부착, sparse 가중치 계산이 전부 오프라인에서 끝나 있고, 질의 때는 이미 만들어둔 인덱스를 조회만 한다.

층위 2

기술 선택의 근거

각 결정을 "무엇을 골랐나 / 대안은 무엇이었나 / 왜 이걸 골랐나" 세 칸으로 적었다. 이유 칸이 이 문서에서 제일 중요한 부분이다.

벡터 DB — Qdrant

채택
선택
Docker 컨테이너로 로컬 구동. dense·sparse를 named vector로 한 컬렉션에 저장.
대안
Chroma (더 간단), pgvector (기존 DB 재활용), FAISS (라이브러리)
이유
sparse 벡터를 네이티브로 지원하고 RRF 융합을 서버가 해준다. Chroma·pgvector였다면 어휘 검색용 BM25 인덱스를 따로 세우고 융합 코드를 직접 짜야 했다.

임베딩 — BAAI/bge-m3

채택
선택
1024차원 dense + lexical sparse를 한 번의 추론으로 동시 추출.
대안
OpenAI text-embedding-3, ko-sbert, KURE-v1
이유
한 모델이 두 표현을 다 준다 — 별도 BM25 없이 하이브리드가 공짜로 성립한다. 한국어도 강해서 "에타에 홍보"가 "에브리타임 홍보"를 1위로 잡았다. OpenAI는 외부 전송이라 자체 서버 요구와 충돌.

하이브리드 검색 — dense + sparse

채택
선택
두 검색을 각각 상위 30개씩 뽑은 뒤 융합해 최종 8개.
대안
dense 단독 (의미 검색만)
이유
둘의 실패 지점이 정반대다. dense는 Zustand, 3차 스프린트 같은 고유명사에 약하고, sparse는 표현이 다른 같은 뜻에 약하다. 팀 위키는 고유명사 덩어리라 dense만으로는 구멍이 크다.

융합 방식 — RRF

채택
선택
Reciprocal Rank Fusion. 점수가 아니라 순위로 합친다.
대안
점수 가중합 (0.7·dense + 0.3·sparse)
이유
dense는 코사인 유사도(0~1), sparse는 가중치 합(상한 없음)이라 두 점수는 애초에 같은 단위가 아니다. 그냥 더하면 스케일 큰 쪽이 이긴다. 정규화하려면 튜닝할 상수가 생기는데, 순위로 합치면 그 문제가 사라진다.

리랭커 — 넣지 않음

보류
선택
cross-encoder 재정렬 단계를 생략했다.
대안
bge-reranker-v2-m3로 상위 20개 재정렬
이유
CPU에서 cross-encoder는 20개 재정렬에 수 초가 든다. 지금은 필요하다는 증거가 없다. Recall@10은 높은데 Recall@5가 낮은 게 측정으로 확인되면 그때 넣는다.

LLM — EXAONE 3.5 2.4B

채택
선택
Ollama로 로컬 CPU 추론. LG의 한국어 특화 모델.
대안
qwen3:1.7b, qwen3:4b, gemma3
이유
세 유형으로 실측해서 골랐다. 아래 표 참조. 추론(thinking) 모델이 아닌 것도 중요한 조건이었다.

모델 실측 — 크다고 좋은 게 아니다

모델평균 응답근거 종합사실 조회없는 것 거절
exaone3.5:2.4b 7.7초 근거 전부 반영 정확 정확
qwen3:1.7b 5.1초 일부 누락, 문장 어색 정확 정확
qwen3:4b 206.7초 답변 실패 — 3,501자를 사고만 하다 토큰 상한 도달

가장 값비쌌던 교훈

Qwen3는 하이브리드 추론 모델이라 사고 과정을 꺼야 하는데, think=False가 모델마다 다르게 동작한다. 1.7b는 실제로 사고를 끄지만, 4b는 사고를 끄지 않고 그걸 content로 흘려보낸다 — 답변 자리에 영어 사고 과정이 그대로 찍힌다.

think를 아예 안 보내면 사고가 별도 thinking 필드로 분리되지만, 이번엔 사고 토큰이 출력 예산을 다 먹어 답변에 도달하지 못한다. 이 하드웨어에서 4B급 추론 모델은 느린 게 아니라 동작하지 않는다.

그래서 llm.py는 해당하는 모델에만 think=False를 보낸다. 이 기능이 없는 모델에 보내면 서버가 거부하기 때문이다. 

THINKING_MODEL_PREFIXES = ("qwen3", "deepseek-r1", "gpt-oss", "magistral")

if config.OLLAMA_MODEL.startswith(THINKING_MODEL_PREFIXES):
    kwargs["think"] = False

인터페이스 — 디스코드

팀이 이미 디스코드를 쓰고 있어서 별도 UI 없이 바로 붙는다. 웹 UI를 만들었다면 호스팅·인증·프론트엔드가 전부 추가 작업이 됐을 것이다. 사용자가 이미 있는 곳으로 가는 게 사용자를 새 곳으로 부르는 것보다 싸다.

층위 3

파일 구조

폴더가 파이프라인 단계를 그대로 반영한다. 의존은 한 방향으로만 흐른다.

src/ ├─ config.py 설정 · 차단 목록 · ID 정규화 ├─ notion/ ── 수집 │ ├─ client.py 트리 순회 · 레이트리밋 · 재시도 · 캐시 │ └─ markdown.py 블록 → 마크다운 ├─ indexing/ ── 인덱싱 │ ├─ chunker.py 계층 청킹 · 컨텍스트 헤더 │ ├─ embedder.py BGE-m3 dense + sparse │ └─ pipeline.py 배치 임베딩 → 저장 ├─ retrieval/ ── 검색 │ ├─ store.py Qdrant 컬렉션 · upsert · 삭제 │ └─ search.py 하이브리드 검색 · RRF ├─ generation/ ── 생성 │ ├─ prompt.py RAG 프롬프트 · 인용 규칙 │ └─ llm.py Ollama 스트리밍 ├─ bot/ │ └─ discord_bot.py 슬래시 커맨드 · 진행 표시 · 출처 임베드 └─ eval/ ├─ golden_set.jsonl 정답 세트 30문항 └─ run_eval.py Recall@k · MRR scripts/ ├─ index.py 최초 전체 인덱싱 ├─ sync.py 변경분만 재인덱싱 └─ ask.py CLI 질의 (봇 없이 테스트)

의존 방향

config      ←  모두가 참조, 아무것도 참조 안 함

notion      →  config
indexing    →  config, notion       (NotionPage를 받아 Chunk를 만든다)
retrieval   →  config, indexing     (Chunk와 Embedding을 저장한다)
generation  →  config, retrieval    (SearchResult를 프롬프트에 넣는다)
bot         →  전부

역방향 참조가 없다. indexing은 retrieval을 모르고, retrieval은 generation을 모른다. 그래서 검색만 따로 테스트할 수 있고 (ask.py --retrieval-only), LLM 없이 Recall 측정이 가능하다.

스크립트가 셋인 이유

스크립트언제하는 일
index.py 최초 1회 만나는 페이지를 전부 청킹·임베딩. --dry-run으로 수집 대상만 미리 확인 가능.
sync.py 주기적 · 중단 후 재개 Qdrant의 last_edited_time과 비교해 안 바뀐 페이지는 임베딩을 건너뛴다.
ask.py 개발 중 봇·디스코드 없이 검색과 답변을 CLI에서 확인. 검색만 볼 수도 있다.
층위 4

핵심 구현 셋

나머지는 표준적인 RAG 코드다. 이 세 가지가 이 프로젝트만의 판단이 들어간 부분이다.

하나 — 컨텍스트 헤더 청킹

이게 이 프로젝트에서 가장 중요한 아이디어다. 노션 문서는 본문이 짧고 정보가 제목과 계층에 몰려 있다. "기술 선정" 페이지 본문에 "Zustand를 골랐다"만 있고, 그게 프론트엔드 얘기라는 사실은 조상 페이지 이름에만 있다.

그래서 청크마다 조상 경로와 헤딩 경로를 본문 앞에 붙여서 임베딩한다. 

[팀 - 모꼬지 > 문서 > 프론트엔드 > 기술 스택 선정 및 선정 이유] 선정 결과 > 상태관리
Zustand를 선택했다. Redux는 보일러플레이트가 많아...

이러면 "프론트 상태관리 뭐 썼어?"라는 질문이 본문에 없는 단어들과도 매칭된다. 답변할 때는 이 헤더를 떼고 location으로 따로 표시한다 — 중복을 피하고 사용자에게는 경로가 더 읽기 좋은 형태로 보인다.

청킹 파라미터

값설정이유
512최대 토큰임베딩 모델이 한 번에 소화하는 양. 넘으면 슬라이딩 분할.
128최소 토큰이보다 짧은 섹션은 인접 섹션과 병합. 노션엔 한 줄짜리 토글이 많다.
64겹침분할 경계에 걸친 문장이 양쪽 어디에서도 안 잡히는 걸 막는다.

분할은 토큰이 아니라 줄 단위로 한다. 토큰 경계에서 자르면 단어가 쪼개져 읽을 수 없는 청크가 나온다. 한 줄이 통째로 예산을 넘을 때만 토큰 단위로 내려간다.

둘 — 증분 동기화

비용의 대부분은 노션 API가 아니라 CPU 임베딩이다(청크당 약 2초). 그래서 "증분"의 기준을 API 호출이 아니라 임베딩에 둔다.

sync.py는 트리 전체를 순회한다 — 이동·삭제를 정확히 잡으려면 필요하다. 대신 각 페이지의 last_edited_time을 Qdrant에 저장된 값과 비교해서 같으면 청킹·임베딩을 건너뛴다. 

known = store.indexed_page_versions()      # page_id → last_edited_time

for page in collector.walk():
    seen.add(page.page_id)
    if known.get(page.page_id) != page.last_edited_time:
        changed.append(page)                  # 이것만 다시 임베딩

removed = set(known) - seen                   # 노션에서 사라진 페이지

갱신은 페이지 단위로 전체 삭제 후 재삽입한다. 부분 갱신보다 단순하고, 페이지가 짧아졌을 때 옛 청크가 남는 사고를 원천 차단한다.

실전 규칙

최초 인덱싱이 중간에 끊겼다면 index.py를 다시 돌리면 안 된다 — 이미 들어간 356페이지를 전부 다시 임베딩한다. sync.py로 이어가야 한다.

셋 — 다중 차단

노션에는 계정 정보, 카드 정보, 회비 내역, 개인 평가가 섞여 있다. 이게 인덱스에 들어가면 누구나 챗봇으로 꺼내볼 수 있다.

방어선수단막는 것
1차 노션 integration을 해당 페이지에 연결하지 않음 애초에 API가 데이터를 못 받는다
2차 BLOCKED_PAGES ID 목록 1차가 실수로 풀렸을 때
3차 BLOCKED_TITLE_KEYWORDS 새로 생긴 민감 페이지가 목록에 없을 때

차단된 페이지는 하위 트리 전체가 함께 빠진다. 부모가 민감하면 자식도 대개 민감하다.

여기에 성격이 다른 목록이 하나 더 있다. EXCLUDED_PAGES는 민감하진 않지만 팀 문서가 아닌 것 — 동아리 모집글 DB와 데이터 백업이다. 왜 뺐는지는 층위 5에 있다.

인덱싱 후에는 검증을 돌린다. 마지막 감사에서 민감 페이지 10개, 범위 제외 2개 모두 0청크였다.

층위 5

실제로 깨진 것들

코드를 읽는 것만으로는 안 보이는 부분이다. 전부 실행해보고 나서야 드러났다.

컨텍스트 헤더가 내용과 어긋남

청킹
증상
"상태관리" 내용을 담은 청크에 헤더가 배경으로 붙었다.
원인
짧은 섹션 병합 로직이 뒤따르는 긴 섹션까지 빨아들였다. 합쳐진 청크가 첫 섹션의 헤딩 경로를 물려받았다.
교훈
병합 조건에 "다음 섹션도 짧을 것"을 넣어야 했다. 헤더가 검색 정확도의 핵심인데 그게 거짓이면 청킹 전체가 역효과다.

형제 헤딩이 조상으로 쌓임

청킹
증상
헤딩 경로가 배경 > 선정 결과 > 상태관리로 나왔다. 배경은 형제 H2인데 조상 자리에 있다.
원인
헤딩 스택을 제목만 담고 레벨을 안 들고 있었다. 노션 문서는 H1 없이 H2로 시작하는 경우가 많아 인덱스 기반 절단이 어긋났다.
교훈
(레벨, 제목) 쌍으로 저장하고 레벨로 절단하면 문서가 몇 단계에서 시작하든 맞는다.

동아리 데이터가 인덱스를 삼킴

범위
증상
281페이지를 수집했는데 218개가 동아리 모집글이었다. 회의록·기획·온보딩에는 도달조차 못 했다.
원인
모집글 DB가 동아리 × 학기 조합으로 137자짜리 유사 페이지를 수백 개 만들어낸다. 이건 팀 문서가 아니라 서비스가 다루는 데이터다.
교훈
인덱싱 전에 --dry-run으로 규모를 먼저 본다. 대형 DB 하나가 검색 품질을 수적으로 압도할 수 있다.

SDK가 API 세대를 갈아탐

수집
증상
DatabasesEndpoint object has no attribute 'query'
원인
notion-client 3.x가 data source 기반 API로 넘어가면서 databases.query를 없앴다. 이제는 DB를 조회해 data_sources를 얻고 그걸 쿼리한다.
교훈
SDK 버전을 문서로 확인하기보다 dir()로 실제 객체를 찍어보는 게 빨랐다.

네트워크 한 번 끊김에 수집 전체가 죽음

수집
증상
20분간 모은 300페이지가 전송 오류 한 번에 통째로 사라졌다.
원인
재시도가 HTTP 상태 코드만 보고 있어 httpx.TransportError를 안 잡았다. 캐시도 순회가 끝나야 저장됐다.
교훈
수백~수천 요청을 보내는 작업은 중단을 정상 경로로 취급해야 한다. 전송 계층 예외도 재시도 대상에 넣고, 캐시는 25페이지마다 저장한다.

공통점

다섯 개 중 넷이 실제 데이터를 넣어보고 나서야 드러났다. 합성 데이터로 짠 테스트는 전부 통과했었다. 노션 문서가 H2로 시작한다는 것, 동아리 DB가 그렇게 크다는 것, 네트워크가 20분 안에 한 번은 끊긴다는 것 — 전부 실제 실행이 알려준 사실이다.

골든 세트를 손봐야 한다

golden_set.jsonl에 30문항이 있지만 전부 "그 문서 어디 있어" 류의 위치 찾기 질문이다. 문서 제목만 보고 만든 거라 난이도가 낮아서, 지금 측정하면 실제보다 좋은 수치가 나온다.

실제 문서를 읽고 이런 유형을 섞어야 의미 있는 숫자가 된다.

  • 사실 조회 — "3차 스프린트 리딩 누구였어?"
  • 이유 설명 — "왜 Zustand 대신 그걸 골랐어?"
  • 여러 문서 종합 — "온보딩 때 프론트랑 백엔드가 공통으로 보는 문서는?"

개선은 싼 것부터

측정 없이 큰 것부터 건드리면 시간을 버린다. 순서를 지킨다.

  1. 청킹 파라미터 — CHUNK_MAX_TOKENS, CHUNK_MIN_TOKENS, 헤더 형식
  2. 검색 폭 — SEARCH_PREFETCH_LIMIT, SEARCH_TOP_K
  3. 프롬프트 — 인용 규칙, 답변 길이
  4. 리랭커 추가 — Recall@10은 높은데 Recall@5가 낮을 때만
  5. 임베딩 파인튜닝 — 도메인 용어를 못 잡는 게 확인될 때만

각 단계마다 run_eval.py로 수치를 확인하고 넘어간다. 이 순서가 층위 0의 결론과 이어진다 — LLM 파인튜닝은 이 목록에 없다.

모든 수치는 2026년 8월 21–22일 이 하드웨어에서 측정했다. 인덱싱은 356페이지 / 922청크 시점에 중단했고, 인덱스는 qdrant_storage/에 보존돼 있다.
